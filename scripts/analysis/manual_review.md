Hand review of `data/analysis/audit_sample.csv` (110 rows: 10 per class) against the raw evidence, plus the automatic checks above (snapshot of the run before the final census pass; the automatic numbers in section 7 are recomputed on every run, this text is not).

- **Location classes (ipfs / http / arweave / on-chain / broken)**: 0 of 110 sampled rows misclassified; the independent regex re-classification of all random-stratum tokens found no on-chain/off-chain confusion. Edge cases that depend on judgement: malformed CIDs (`ipfs://0`, truncated CID, CID with the token id glued on, relative `ipfs/Qm...`) are census `broken` or `http`; I would call them "malformed ipfs", which does not change any on-chain share.
- **data-uri vs onchain-renderer split** (30 vs 122 in the random stratum) is census's heuristic (bytecode / gas / source hints). Both count as on-chain everywhere in this analysis; do not quote the split as a finding.
- **Truly on-chain (census-level)**: the 10 sampled rows are all on-chain JSON + data: image, no external refs. The census flag does not execute JavaScript art, so for HTML/JS pieces "renders unplugged" is only confirmed for collections also in the gallery gallery. Treat 'truly on-chain' as an upper bound for rendering.
- **Liveness**: 0 evidence inconsistencies (every `alive` has a 2xx fetch, no `dead` with any alive fetch). Live DNS recheck (snapshot): 22 of 25 sampled DNS-dead hosts still fail; 3 now resolve (re-registered, parked or a transient resolver failure at census time), so the DNS-dead label may be ~10% soft. dead_hosts.csv rows for DNS should be re-verified by hosts (WHOIS/registrability). Two weaknesses, not misclassifications: (1) `ipfs-not-found` dead (`gateway-not-found:http-504`) means "no public gateway returned the CID within 15-40 s", which is weaker than DNS death (reported separately as soft dead); (2) a collection is `dead` if its two sampled ids both fail, so one unminted/burned id range can push a live collection to `degraded`/`dead` (see 'FOREVERYOUNG: CozyKidz' degraded by a single reverting token).
- **tokenURI-revert is 4.7% of the random stratum** (census `broken`): contract calls revert on every sampled id on all nodes. These are counted dead (not 'dead server'); they are a mix of unrevealed/paused collections, burned id ranges and contracts without tokenURI. Reported separately in the reasons table.
- **Media location is unresolved** for ~28% of the random stratum because the off-chain metadata (dead or unfetched) could not be read. Blockscout's cached instance image rescues some (`media_class_source=blockscout-cache`). The site gets `unresolved` for these (schema request 1, implemented in the site data).
- **What census should fix / could improve**: (a) pass 2 is still reducing `unknown` (timeouts, `dead-candidate`); rerun this pipeline on the final parquet. (b) Consider counting a collection `alive` when >=1 sampled token is alive and the others revert, or sampling a third id for collections with reverts. (c) `external_refs`/`has_external_refs` is only meaningful for on-chain payloads; in the parquet the column is also filled for off-chain rows, which is confusing. (d) `meta_hardcoded_gateway_state` `untested` for hostnames like `*.mypinata.cloud` (dedicated gateways) leaves exact-URL liveness `unknown`.
- **Reclassification rules applied in this analysis layer**: only (1) `media_class='none'` with no media source -> `unresolved` (not 'no media field'); (2) claims claim strengths: `explicit-100%/fully` + `storage-forever` -> explicit tier, `on-chain-generic` -> generic tier, `implied` excluded (claims says not to test them); (3) `total_supply` outside 1..1e6 treated as unknown for token weighting (this drops ShineCoin, 4.0M "tokens" for 128 holders, which otherwise carries 38% of the ERC-721 token weight); (4) claims addresses de-duplicated case-insensitively (440 distinct, not 513). No census verdict was overridden.
